環境建置 先做這步

跑任何測試之前，這幾件事要先就位。

app/ 加入 vitest devDependency，新增 vitest.config.js（沿用現有 vite.config.js 的 alias/plugin 設定） app/vitest.config.js

worker/ 目前沒有 package.json，要先建立一份，加入 vitest 與 @cloudflare/vitest-pool-workers（讓測試在真的 Workers runtime 裡跑，含 caches 這類 Worker 專屬 API） worker/package.json

加入 @playwright/test，設定對 npm run dev（Vite dev server）跑 E2E，先只跑 Chromium 一個瀏覽器 app/playwright.config.ts

三個套件都加上 npm run test / test:e2e script，方便之後串 CI（CI 本身這次不規劃，見下方 Out of Scope）

單元測試 — app 核心計算 最高風險

這些函式錯了，使用者會看到錯的餘額、錯的損益，而且不會有任何警訊——是整個 App 最值得優先顧的地方。

目標優先度為什麼該覆蓋的案例
computeAccounts()P0 所有帳戶餘額、淨資產的唯一計算來源 初始餘額、收支加減、轉帳含手續費、未來日期紀錄跳過、信用卡負號顯示、股票買進雙軌（有/無自動轉帳流）
computeHoldings()P0 FIFO 配對錯一次，均價/損益全部跟著錯 單純買賣、部分賣出後均價重算、賣光後從清單消失、無即時股價時退回最後成交價、跨幣別換算
ffExportBackup / ffImportBackupP0 備份救不回來等於資料全毀，且不會有錯誤訊息提早提醒 加密/解密往返後資料完全一致、密碼錯誤要明確報錯、salt/iv 每次都不同、大量資料不超出 storage 配額
main.js schema migrationP0 升級版本時如果 migration 壞掉，是舊資料整批壞掉 舊版本資料升級到 v4 後結構正確、重複跑 migration 要是 idempotent（不能跑兩次壞掉）
StockForm 手續費／證交稅計算P1 算錯金額使用者自己看得出來，風險比上面幾項低 依券商費率/折扣算手續費、四種證交稅預設稅率、手動覆蓋優先於自動計算
parseUtterance()（語音解析）P1 規則多、最容易改壞，但解析錯使用者確認畫面就看得出來 股票買賣關鍵字、轉帳雙帳戶切分、中文數字金額（張/股）、分類模糊比對、辨識失敗時退回文字輸入

單元測試 — worker 股價服務 中風險

算錯不會毀資料，但會讓使用者看到錯的市值——用 vitest-pool-workers 搭配 mock fetch，不真的打外部 API。

目標優先度該覆蓋的案例
getMIS / getDailyAll 備援鏈P1 即時報價缺漏時退回收盤價、TWSE 缺的再查 TPEx／興櫃
getUS / getYahoo 備援鏈P1 未設定 FINNHUB_KEY 時全部走 Yahoo、Finnhub 查不到的個股退回 Yahoo
/quotes、/stocks 路由P1 回應格式（prices/fx/source）正確、CORS header 存在、未知路徑回 404

E2E — 關鍵使用者流程

用 Playwright 實際點畫面，驗證從「使用者操作」到「畫面顯示結果」這一整條路是通的——單元測試顧邏輯，這裡顧串接。

  1. 記一筆支出 → 資產頁餘額正確扣掉P0
    最基本、最高頻的使用路徑，任何回歸都會第一時間被使用者發現
  2. 記一筆股票買進 → 投資頁出現新持倉、手續費金額正確顯示P0
    串起表單輸入、手續費計算、FIFO 建倉三件事，任一環壞了這條會抓到
  3. 加密備份匯出 → 清除所有資料 → 用密碼匯入 → 資料與匯出前一致P0
    是「不上雲」架構下使用者唯一的救命索，壞掉等於資料歸零
  4. 設定 App 鎖 PIN → 重新整理頁面 → 要求輸入 PIN 才能看到資料P1
    安全性功能，壞掉的後果是「形同虛設」而非資料損毀，優先度稍低
  5. 清除所有歷史資料 → 主檔設定（帳戶/分類/券商）保留、交易紀錄清空P1
    驗證 FF_CLEAR_KEYS 的清單沒有清錯範圍——多清或少清都是使用者資料事故
Out of Scope（這次不規劃）
